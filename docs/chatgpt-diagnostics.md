# ChatGPT connection diagnostics

[English](chatgpt-diagnostics.md) | [日本語](chatgpt-diagnostics.ja.md)

`mcp-interop diagnose --profile chatgpt` checks whether a Remote MCP server's published OAuth metadata is compatible with ChatGPT's documented MCP authentication flow.

It is a **preflight diagnostic**, not a ChatGPT live adapter. It does not create a ChatGPT app, press **Scan Tools**, complete OAuth inside ChatGPT, or claim a real-client `reach/auth/init/tools` PASS.

## Basic usage

```console
mcp-interop diagnose https://example.com/mcp --profile chatgpt
```

Machine-readable output:

```console
mcp-interop diagnose https://example.com/mcp --profile chatgpt --json
```

The current ChatGPT profile checks:

- HTTPS Remote MCP endpoint;
- OAuth 2.0 Protected Resource Metadata discovery from `WWW-Authenticate` or the standardized well-known locations;
- advertised `authorization_servers`;
- OAuth Authorization Server Metadata / OpenID Connect discovery with matching `issuer`;
- `authorization_endpoint` and `token_endpoint`;
- client registration strategy:
  - Client ID Metadata Documents (CIMD), or
  - Dynamic Client Registration (DCR) fallback;
- CIMD token endpoint authentication compatibility (`none` or `private_key_jwt`);
- PKCE `S256` advertising;
- `offline_access` advertising as a refresh-token/connectivity advisory;
- the Protected Resource Metadata `resource` value relative to the supplied MCP endpoint.

A server that advertises:

```json
{
  "client_id_metadata_document_supported": true,
  "token_endpoint_auth_methods_supported": ["none", "private_key_jwt"]
}
```

can pass ChatGPT registration preflight **without** a `registration_endpoint`. ChatGPT can use CIMD and does not require DCR for that path.

## Verify the exact ChatGPT client metadata

If your authorization-server logs contain the **sanitized** authorization request generated by ChatGPT, the `client_id` and `redirect_uri` are useful non-secret evidence. Do not copy `code`, `state`, tokens, cookies, or client assertions.

Pass the exact observed values:

```console
mcp-interop diagnose https://example.com/mcp \
  --profile chatgpt \
  --client-id 'https://chatgpt.com/oauth/.../client.json' \
  --redirect-uri 'https://chatgpt.com/connector/oauth/...'
```

When `--client-id` is supplied, the diagnostic also:

- fetches the CIMD document;
- compares client and authorization-server token endpoint authentication methods;
- verifies the observed redirect URI is listed in the CIMD document when `--redirect-uri` is supplied;
- fetches/checks the advertised JWKS when `private_key_jwt` is a compatible method.

This is particularly useful when OAuth reaches the authorization endpoint but fails before or during token exchange.

## Reading the result

Text output is explicitly labeled either:

```text
PREFLIGHT PASS
```

or:

```text
PREFLIGHT FAIL
```

A warning does not make the preflight fail. For example, absence of `offline_access` is advisory because initial authorization can still succeed, but ChatGPT may later lose connectivity when the access token expires if refresh tokens cannot be obtained.

Even a complete `PREFLIGHT PASS` does **not** prove that the real ChatGPT client completed OAuth or tool discovery. It means the public server/client metadata visible to the diagnostic contains no currently known blocking mismatch for the selected profile.

## If preflight passes but ChatGPT still fails

Use authorization-server and MCP resource-server logs to identify the next boundary. Keep all shared output sanitized.

Check whether the actual ChatGPT flow reaches these points:

1. Authorization request arrives with the expected `client_id`, exact `redirect_uri`, PKCE challenge, scopes, and `resource`.
2. If using CIMD, your authorization server fetches and validates the ChatGPT client metadata document.
3. If using `private_key_jwt`, the token request includes a client assertion that validates against the ChatGPT JWKS, with correct `iss` / `sub` / `aud` / `exp` / `jti` handling required by your authorization server.
4. Token exchange receives the PKCE `code_verifier` and the same protected-resource `resource` value.
5. The token response is accepted and, for durable connectivity, a refresh token is issued when your policy expects one.
6. A subsequent MCP request arrives with `Authorization: Bearer ...` and the MCP server accepts its signature, issuer, audience/resource, expiry, and scopes.
7. ChatGPT proceeds to MCP initialization/tool discovery.

Do not paste authorization codes, access/refresh tokens, cookies, private keys, raw client assertions, or short-lived OAuth `state` into an issue.

## Current boundary

`mcp-interop` does not currently have a supported headless ChatGPT app-management surface equivalent to the Codex app-server or Cursor MCP management commands. The project therefore keeps ChatGPT as a research target for true real-client automation rather than using brittle browser DOM automation.

- OpenAI plugin authentication: `https://developers.openai.com/plugins/build/auth`
- OpenAI ChatGPT developer mode / MCP apps: `https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt`
